# PR Comment Bot — Design Document

## What It Does

Automatically posts a summary comment on Pull Requests showing what AI agents did during development of that PR. Gives reviewers instant visibility into AI-generated code without reading logs.

---

## The Problem It Solves

When a PR arrives for review, the reviewer has no idea:
- How much of the code was AI-generated vs human-written
- Whether the AI agent accessed secrets, hit guardrails, or was killed mid-session
- How many sessions/iterations it took (was the AI struggling?)
- Whether any critical threats or warnings fired during development

The PR comment bot bridges this gap by surfacing tracker data directly in the code review workflow.

## How It Works

### 1. Branch → Sessions Mapping (Already Implemented)

The tracker already records `git_branch` on every session. The watcher detects the active branch at session start. This gives us:
- `getSessionsByBranch(branchName)` — all sessions for a branch
- `getBranchSummary(branchName)` — aggregated stats

### 2. PR Webhook Trigger

When a PR is opened/updated, a webhook fires to the tracker:

```
POST /api/pr-comment
{
  "platform": "github",       // or "gitlab", "bitbucket"
  "repo": "owner/repo",
  "pr_number": 42,
  "branch": "feature/new-auth-flow",
  "action": "opened"          // or "synchronize" (new push)
}
```

This can be triggered by:
- **GitHub Actions** — a workflow that calls the tracker API on PR events
- **GitHub App/Webhook** — direct webhook from GitHub to the tracker
- **CLI command** — `al-tracker pr-comment --branch feature/foo --pr 42`

### 3. Comment Generation

The tracker:
1. Looks up all sessions for the PR branch
2. Aggregates events, alerts, trust scores
3. Formats a Markdown comment
4. Posts it via the platform API (GitHub REST API, GitLab API, etc.)

### 4. Authentication

- **GitHub:** Personal Access Token or GitHub App installation token stored in config
- **GitLab:** Project access token
- **Bitbucket:** App password

Stored in `config.json` under a new `prBot` section:

```json
{
  "prBot": {
    "enabled": false,
    "platform": "github",
    "token": "",
    "repo": "owner/repo",
    "commentOn": "open",
    "includeSessions": true,
    "includeAlerts": true,
    "includeTrustScore": true,
    "minSeverityToReport": "warn"
  }
}
```

## Implementation Plan

### Phase 1: Core Comment Generator
- `src/pr-bot/index.ts` — main module
- `generatePRComment(branch: string): string` — builds the Markdown comment from session/alert data
- `getPRSummary(branch: string): PRSummary` — structured data for the comment

### Phase 2: Platform Adapters
- `src/pr-bot/github.ts` — GitHub REST API (create/update comment)
- `src/pr-bot/gitlab.ts` — GitLab merge request notes
- `src/pr-bot/bitbucket.ts` — Bitbucket PR comments

Each adapter implements:
```typescript
interface PRPlatformAdapter {
  postComment(prNumber: number, body: string): Promise<void>;
  updateComment(commentId: number, body: string): Promise<void>;
  findExistingComment(prNumber: number): Promise<number | null>;
}
```

The bot updates the same comment (idempotent) rather than posting duplicates.

### Phase 3: Trigger Mechanisms
- **API endpoint:** `POST /api/pr-comment` — for webhooks/CI
- **CLI command:** `al-tracker pr-comment --branch <branch> [--pr <number>]`
- **Auto-trigger:** When a session ends on a branch that has an open PR (optional, requires polling)

### Phase 4: GitHub Actions Integration
Provide a reusable workflow file:

```yaml
# .github/workflows/ai-tracker-pr-comment.yml
name: AI Agent Summary
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  comment:
    runs-on: ubuntu-latest
    steps:
      - name: Post AI Activity Summary
        run: |
          curl -X POST http://localhost:3847/api/pr-comment \
            -H "Content-Type: application/json" \
            -d '{"platform":"github","repo":"${{ github.repository }}","pr_number":${{ github.event.pull_request.number }},"branch":"${{ github.head_ref }}"}'
```

## What Reviewers Get

1. **At a glance:** Was AI heavily involved? Any red flags?
2. **Trust signal:** If the AI trust grade is C or below, reviewers know to be more careful
3. **Alert visibility:** Any sensitive file access or dangerous commands are called out
4. **Session count:** Many sessions = AI struggled = review more carefully
5. **Compliance proof:** For regulated teams, this is audit evidence in the PR itself

---

## Dependencies

- Git branch tracking (✅ already implemented)
- Session aggregation by branch (✅ already implemented)
- Alert/trust data per session (✅ already implemented)
- Platform API tokens (new config field)
- HTTP client for API calls (can use built-in `fetch` or `node-fetch`)

---

## Security Considerations

- Token stored in config (not committed to repo) — should support env var override `AL_TRACKER_PR_TOKEN`
- Comments only contain aggregated metadata, never raw logs or file contents
- Sensitive file paths can be redacted based on config
- Rate limiting on the API endpoint to prevent abuse
